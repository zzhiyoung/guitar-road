# Creator OMR 与 TAB 工具开发计划

日期：2026-10-02。状态：**用户已授权主程序集成；P3–P4 已实验接入 Creator，P2 扩展样本出口与新文件用户验收尚未完成**。先前的阶段门槛仍作为正式支持的验收要求；当前以实验能力提供，并明确拒绝不可靠的对齐。

当前实现、实测结果与未通过项见 [CREATOR_OMR_PROGRESS.md](CREATOR_OMR_PROGRESS.md)。下文的阶段出口条件与目标仍作为验收要求，不代表现有能力。

## 1. 目标与范围

让教材中的“五线谱 + 六线谱”片段转换为可在 alphaTab 预览、播放，并在 Guitar Pro 继续校正的 MusicXML 草稿，保留原稿弦号和品位，不生成虚假的第二乐器或低音声部。

原 SPEC 第一阶段暂不实现 TAB OCR；Phase 2 的 B 路线为“五线谱可用但 TAB 不行 → 开发 TAB parser”。本计划落实这一候选，并同时处理已发现的五线谱质量问题。专辑管理、整曲播放已由用户验收；本轮开发集中在 Creator 和可选 Python sidecar。

第一版支持边界：

- 清晰印刷体 PNG/JPG、标准六弦吉他 EADGBE 调弦。
- 同一行系统中成对出现的五线谱与 TAB，允许多个这样的行系统，目标输入 4–16 小节。
- 单音旋律；先覆盖现有八分音符练习，再用四分音符和休止符扩展验证。其他时值只有通过样本验证后才列为支持。
- TAB 原始弦号、一位/两位品位数，支持 0–24 品；时值来自对应五线谱，不能从数字横向间距猜拍长。
- 五线谱单独输入可继续使用；独立纯 TAB 的节奏解析不属于首版能力。

首版不承诺和弦/多声部 TAB、击勾弦/滑音/推弦、非标准调弦/变调夹、手写谱、拍照透视、PDF/整本批处理、左右手文字指法、完整修谱编辑器。识别到无法处理的结构时应报告范围限制，不能静默丢弃。特别是原稿下方的拨弦与左手文字，不等同于弦号/品位，本轮不做文字指法 OCR。

## 2. 已知基线

目前只有三个用户提供的两小节片段，不能据此推断所有教材的准确率。

- 完整原图：TAB 区域被误读成额外谱表/声部，输出没有弦号和品位信息。
- 隔离 TAB 后：三张都恢复为单谱表、2 小节、16 个八分音符；人工候选标注分别发现 3、1、3 处音高差异，集中在还原号与低音附加线。
- 上述手工标注尚未由用户独立确认；这些识别产物的 Guitar Pro 导入与修正耗时尚未验收。另制作的原创四音兼容性 fixture 已由用户确认在 Guitar Pro 8 可用，详见进展记录。

原图、裁剪图、JSON、MusicXML、脚本和人工候选标注保留在本地评测目录，不进入公共 Git 仓库。技术和业务验收分别记录；接口 ok=true 不表示识别正确。

## 3. 处理链路

```text
图片
  → 定位并配对五线谱 / TAB 区域
  → 五线谱区域交给 homr：小节、时值、休止符、候选音高
  → TAB 区域交给自写 parser：弦号、品位、位置、候选及质量标记
  → 在同一行系统、同一小节内对齐音符事件
  → 核对节奏、弦/品位与音高，输出冲突或融合结果
  → MusicXML 草稿
  → alphaTab / Guitar Pro 验证
```

五线谱与 TAB 解析可分别调试。融合后表达同一吉他音乐内容；根据消费者支持选择单谱表技术标记或语义关联的标准谱/TAB 谱表，不能作为两个独立演奏声部重复发声。

五线谱区域定位要保留谱号、升降号、符干、连梁及附加线。不能通过固定高度裁剪推广到所有输入，也不能在 XML 中一律删掉第二谱表，这会误伤合法复谱表。

TAB 算法优先采用线检测、数字候选分割和现成数字 OCR 的组合。双位数按同一弦线及几何距离组合，避免把 10 拆成两个事件。先比较现成 OCR 对去线前/后图块的效果；不得破坏与弦线相交的数字。模板匹配可作为小样本比较基线，不能凭三张同版式样本宣布泛化成功。当前不训练模型。

音高核对使用显式调弦；同音可能对应多个弦/品位组合，必须保存原图 TAB 的组合。只有弦归属、数字和对齐均通过质量条件时，才能用 TAB 核对或纠正 homr 的候选音高；保留原始输出和变更记录。条件不足时标为需校对，不自动覆盖。

## 4. 分阶段执行与出口条件

| 阶段 | 工作及交付物 | 进入下一阶段的条件 | 预计开发量 |
| --- | --- | --- | --- |
| P0：基线与格式验证 | 固定引擎版本/参数；整理三个样本的候选标注；制作原创小型 MusicXML，验证吉他八度、弦/品位、预览及 GP 导入 | 对照记录完整；确认一种可在当前 alphaTab 和 GP 保留弦/品位且正确发声的文件表达 | 0.5–1 天 |
| P1：谱面区域隔离 | 实现五线谱/TAB 检测、系统配对、坐标映射和诊断输出；五线谱区域调用 homr | 三个基线不产生虚假第二声部；额外版式验证不截掉升降号或附加线；配对失败能明确报出 | 1–2 天 |
| P2：TAB CLI 原型 | 实现六弦定位、数字分割/OCR、双位数组合、弦归属、小节分组；输出独立 TAB JSON | 三个基线共 48 个弦/品位事件全部正确；额外样本覆盖空弦、两位数、换弦及多个系统 | 2–3 天 |
| P3：对齐与融合 | 对齐 TAB 事件和五线谱时值；导出调弦、弦/品位与正确吉他音高；检查小节与冲突 | 基线逐音保留原弦/品位及八分时值；零虚假声部；数量/位置冲突不能错位强配；预览和 GP 导入验证通过 | 1–2 天 |
| P4：Creator 接入 | 接入已验证 pipeline；增加简单输入模式；补播放/暂停/停止及质量提示 | 上传/粘贴→识别→五线谱+原 TAB 预览→播放→下载可用；缺依赖、超时、不支持布局均可理解 | 1–2 天 |
| P5：扩大评测与验收 | 10–20 个实际用途片段；独立样本评测、GP 校正计时、核心回归、文档与许可证更新 | 达到技术目标，并由用户判断是否节省录谱时间 | 1–2 天，另计人工验收 |

总量约 7–12 个开发日，只作拆解后的工作量估计，不是交付承诺；额外样本准备、GP 人工验收及引擎比较的等待时间另计。首先只推进 P0–P2 到可评估原型，出口条件满足后再融合与接入 UI。

### P0：兼容性风险先验证

- 测试“2 弦 5 品”和“1 弦 0 品”：标准调弦下都发 E4，但弦/品位必须分别保留，不能自动换指法。
- 验证吉他记谱与实际发声的一八度差异。不能仅看五线谱位置正确就认定播放正确。
- 按 MusicXML 规范输出弦/品位和调弦；实测当前安装的 alphaTab 1.8.4，以及用户的 Guitar Pro 版本，而不是只依赖最新网页支持表。
- 明确重复标准谱/TAB 表达的导入行为，排除重复播放或导入成两个乐器。

### P1：五线谱错误定位

保留 homr 原始输出及分割/识别诊断数据，区分还原号漏识别、XML 生成时临时升降号处理错误、附加线造成的音高错误。当前样本只能证明输出错误，尚不能证明是哪一层的 bug。局部适配或上游修复需要对应证据；不把所有音高偏差硬改成某条固定规则。

### P2：独立可检查的 TAB 结果

每个候选事件至少记录 system、bar、string、fret、bbox、横向位置和异常原因。OCR 候选质量不等同于校准后的概率；如使用阈值，必须在调参与留出样本中验证。诊断可视化能看到弦线、数字框和识别值，便于判断错误来自数字还是弦线归属。

不确定数字保留候选/未知状态；不能用 0 品补缺失数字。小节号和系统连接不明确时，不强行把所有事件拼成一首歌。

### P3：对齐规则

按系统及小节约束，对五线谱音符候选与 TAB 位置进行单调对齐。homr 当前输出是否包含可用位置需要在 P0/P1 验证；缺少位置时评估独立音符几何定位，不能假定能获得最新版本的坐标字段。

只比较两边音符数量或按全曲数组下标配对不够：一个漏音就可能让后续全部错位。音符数量、横向位置、休止符或声部关系不一致的小节应标为冲突。不能凭 TAB 的横向间距生成节奏，也不能自动加三连音或补音凑拍。

## 5. 评测与验收

以下为建议目标，应在 P0 定稿；不是现有测试结果。

- **回归基线**：三个样本 48 个 TAB 事件的弦/品位、融合音高及对应时值全部与确认后的标注一致；无额外声部、无缺失或重复事件。
- **独立评测**：共 10–20 个真实用途片段，至少三分之一留出且不参与调参；覆盖不同教材字体、分辨率、扫描质量、两位品位、多系统、空弦及休止符。三个基线只有 6 小节，不足以替代该批评测。
- **识别指标**：独立支持范围内的弦/品位事件正确率和融合音高/时值事件正确率目标分别 ≥98%；漏识别、重复和错位计错，按每个样本和总体分别报告，不能只统计高可信子集。
- **结构指标**：本轮支持样本不生成虚假的第二音乐声部；遇到未知结构明确报告。另以真实复谱表控制样本验证没有误删合法声部。
- **覆盖率**：至少 80% 的范围内片段完成融合草稿；拒绝与需校对数量独立报告，避免靠大量拒绝获取高准确率。覆盖率与正确率都需达标。
- **互操作性**：全部验收输出能在 alphaTab 和 GP 打开；原弦/品位、时值、八度及播放保留。人工 GP 结果单独记录。
- **业务价值**：8–16 小节简单练习沿用原 SPEC 的“校正 ≤3 分钟”目标，建议至少 80% 的适用计时样本达成；记录每个样本耗时及与手工录入的对照。最终是否有用由用户验收。
- **运行可靠性**：保留 20 MB / 120 s 限制，记录超时率和耗时；不能为追求速度降低识别检查。缺 Python、homr 或数字 OCR 时核心应用照常启动。

自动化检查包括区域配对、数字组合、弦线归属、音符对齐、调弦/八度、XML 结构及异常路径。用原创/许可证清晰的小型谱图作公共测试，真实教材样本只在本地评测。

## 6. 停止扩大范围的条件

- 若 P0 不能让弦/品位在预览与 GP 中保留，先解决文件表达/导入兼容性，再做 OCR。
- 若 P2 在独立样本上无法可靠识别数字或弦归属，先比较分割/OCR方案，不接入“已支持 TAB”的 UI，也不直接进入模型训练。
- 若 P3 的主要瓶颈仍是五线谱节奏，不通过音符补齐或强配对掩盖，使用同一批样本评估 homr 与 Audiveris 等候选；候选也必须先实测，不能承诺换引擎就会提升。
- 若支持范围内仍大量需要手动选择区域，明确这是辅助模式；自动区域检测与人工辅助的成绩分别报告。
- 未通过技术与业务验收时不继续扩展 PDF、批量、和弦及高级奏法。

## 7. 实现边界与提交安排

建议模块边界（名称可在实现时调整）：

```text
tools/omr/guitar_road_omr/
  regions.py              谱表、系统、小节定位与配对
  tab_parser.py           六弦定位、数字候选和事件输出
  alignment.py            五线谱/TAB 事件对齐与冲突检查
  musicxml.py             吉他信息融合、XML 校验
  pipeline.py             组合现有引擎与 TAB 工具
tools/omr/tests/           原创确定性测试
tools/omr/benchmark/       评测脚本与指标定义，不存私人原图
```

现有 `HomrEngine` 保持五线谱 adapter；新增组合 pipeline。CLI 的成功/失败 JSON 契约保持兼容，通过可选模式扩展。数字 OCR 依赖属于 sidecar 的可选安装项，不加入核心 npm 依赖；选型在原型结果出来后确定。依赖版本、权重来源和新增许可证记录完整；不直接改 venv 中安装的上游源码来交付。

提交按可独立审查顺序组织：

1. 原创格式 fixture、评测框架及 baseline。
2. 区域检测与五线谱隔离。
3. 独立 TAB parser 与 CLI 原型。
4. 对齐、MusicXML 融合和语义检查。
5. Creator 输入模式、播放控件及质量提示。
6. 验收记录、使用范围和依赖文档。

Creator 可以提供“自动 / 仅五线谱 / 五线谱+TAB”三个简单模式；纯 TAB 暂不显示为受支持输入。诊断功能留在本地开发工具，页面只展示对校对有用的小节/事件提示，不显示服务器路径或内部日志。

Creator 仍不创建 Song、ScoreFile、Block 或 Session。沿用现有播放器、上传大小、超时及独立临时目录。用户真实图片与失败证据通过显式本地评测目录保留；日常上传不新增永久存储。

每次 Python/核心逻辑改动运行相应确定性测试；前端改动运行 typecheck，阶段完成运行隔离 production build。构建与端到端使用临时数据库及独立输出目录，保留现有 `.next` 和练习数据。修改共享播放器时回归 Practice 与整曲播放；没有共享修改也做阶段结束的页面及“不新增练习记录”抽查。

本计划不要求修改 Node 版本、build/start 行为或端口。如果实现确实触及这些内容，必须依 AGENTS.md 更新 launcher 并在隔离副本完成 fresh、already-built、rebuild 三种启动测试。开始写 Next.js 代码前阅读安装版本自带指南。
